# ADR-0348 — Разрешение зависимости `services → dsl`

* Статус: Draft (на согласование)
* Дата: 2026-10-08
- **Затрагивает:** `tools/check_layers.py` (матрица `ALLOWED`), пакет `src/backend/services/dsl_portal/`
- **Связан с:** ADR-0284, ADR-0286, ADR-0196, `CLAUDE.md` §«Ограничения слоёв»

## Контекст

Матрица слоёв в `tools/check_layers.py:70` объявляет:

```python
"services": {"core", "schemas", "infrastructure"},
"entrypoints": {"services", "schemas", "core", "infrastructure", "dsl"},
```

То есть `services` не имеет права импортировать `dsl`, тогда как
`entrypoints` — имеет. При этом **сам проект документирует обратное**:
`src/backend/services/dsl_portal/builder_facade.py` описывает себя как
легитимный потребитель DSL-рантайма, и именно он является публичной точкой
входа для «построить пайплайн из Python».

Фактические зависимости (проверено на HEAD `71529f309`):

- 11 файлов в `src/backend/services/` содержат ссылку на `src.backend.dsl`
  (25 импортов в сумме);
- из них **4 файла** покрыты baseline-allowlist
  (`dsl_portal/builder_facade.py`, `execution/action_dispatcher.py`,
  `ops/webhook_scheduler.py`, `plugins/registries.py`).

Распределение 49 записей baseline-allowlist по слоям:

```
entrypoints  18
services     15
dsl           6
core          5
workflows     3
infrastructure 1
```

Разбивка 15 записей слоя `services` — **основание для решения**:

| Тип | Записей | Пример |
|---|---|---|
| `services → dsl` | 12 | `dsl_portal/builder_facade.py → dsl.engine.pipeline` |
| `services → extensions` | 3 | `io/files.py → extensions.core_entities.files.services.files` |

То есть **80 % долга слоя `services` — это ровно тот класс зависимости,
который проект считает легитимным**. Устранять его правкой кода нельзя,
нужно решение по матрице.

Отдельно: `services/ai/ai_graph.py` содержит ссылку
`"src.backend.dsl.commands.registry"` как **строковый литерал**
(`ai_graph.py:268`), а не как импорт, поэтому статический анализатор её не
видит. Это надо учитывать при любом анализе — «0 нарушений» здесь означает
«не найдено», а не «отсутствует».

## Проблема

Текущая конфигурация порождает два дефекта:

1. **Матрица противоречит документации.** Спецификация слоёв и фактические
   намерения кода расходятся, из-за чего allowlist вынужденно фиксировать
   законные зависимости как «нарушения». Baseline не сходится к нулю даже
   при полном исправлении кода — часть записей невозможно закрыть, не
   меняя саму матрицу.
2. **Allowlist смешивает два разных класса долга.** Запись
   `builder_facade.py → services → dsl.*` — это осознанный архитектурный
   контракт (публичный фасад), а не утечка. Запись
   `core/ai/llm_gateway.py → services.ai.gateway.client` — это реальное
   нарушение правила «core не импортирует код из `src/`». Оба числятся
   одним счётчиком, поэтому метрика «49 legacy» не показывает реальный
   прогресс.

## Рассмотренные варианты

### Вариант A. Добавить `dsl` в `ALLOWED["services"]` и удалить 12 записей

- **Плюсы:** долг схлопывается с 49 до ~37, метрика начинает отражать
  только настоящие утечки; `builder_facade` перестаёт быть «нарушением».
- **Минусы:** `dsl` — meta-layer, буквально импортирующий `services` и
  `entrypoints`. Разрешение `services → dsl` формально делает граф слоёв
  циклическим на уровне пакетов и ослабляет гейт для **всех** новых
  импортов в `services`, а не только для уже существующих.
- **Риск:** цикл не проявляется как ошибка импорта (Python терпит циклы на
  уровне модулей), поэтому деградация будет накапливаться скрытно.

### Вариант B. Вынести фасад в `dsl`, оставив матрицу строгой

Перенести `services/dsl_portal/builder_facade.py` → `src/backend/dsl/portal/builder_facade.py`
и оставить в `services` тонкий re-export для обратной совместимости.

- **Плюсы:** матрица остаётся строгой, цикл разрывается по направлению
  зависимости, новые импорты по-прежнему блокируются гейтом.
- **Минусы:** это **публичное перемещение API** (`services.dsl_portal.builder_facade`
  импортируется в `tools/functional/`, тестах и, возможно, в плагинах) —
  требует соблюдения процедуры смены публичного API.
- **Объём:** нужно найти всех потребителей; затрагивает ~3–5 файлов.

### Вариант C. Разделить baseline на два счётчика, матрицу не трогать

Разделить allowlist на `allowed-contract` (осознанные контракты, например
фасады) и `legacy-debt` (утечки). Гейт считает только `legacy-debt`.

- **Плюсы:** нулевой риск для рантайма и публичного API; метрика становится
  честной без изменения архитектуры.
- **Минусы:** долг по числу не уменьшается; это косметика, если не
  сопровождаться планом снижения.

### Вариант D. Ничего не менять

Оставить 49 записей как есть.

- **Плюсы:** ноль риска.
- **Минусы:** метрика «0 новых, 49 legacy» перестаёт быть полезной —
  невозможно отличить прогресс от стагнации.

## Рекомендация

**Комбинация C + B**: сначала разделить baseline на два класса (C) — это
не трогает рантайм и сразу даёт честную метрику; затем, отдельным решением
с процедурой смены публичного API, выполнить перенос фасада (B).

**Вариант A не рекомендуется**: он убирает симптом ценой ослабления гейта
на будущее, что противоречит принципу «allowlist фиксирует существующий
долг и не должен расти».

## Последствия

- Метрика `tools/check_layers.py` станет «contract-aware» и начнёт
  показывать реальный остаток утечек.
- Потребуется обновление `CLAUDE.md` §«Ограничения слоёв»: фактическая
  матрица и описание `builder_facade` должны быть приведены к одному
  согласованному виду.
- Вариант B затрагивает публичный импорт и по правилам проекта требует
  отдельного согласования до выполнения.

## Критерий приёмки

- [ ] Базовые записи разделены на `contract` и `debt`; гейт падает только на `debt`.
- [ ] `check_layers.py` печатает обе цифры раздельно.
- [ ] Документация слоёв соответствует матрице.
- [ ] Ни одна существующая запись не удалена «подгонкой» (только переводом
      между классами или реальным исправлением кода).
