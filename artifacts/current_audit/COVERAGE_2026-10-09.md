Прежнее задокументированное значение — «60%» (S34 W4, «реалистичная
промежуточная цель») — **не подтвердилось**: фактический baseline выше на
14 п. п. Расхождение, вероятно, накопилось из-за нескольких обновлений
baseline «на глаз», а не измерялось сквозным прогоном: монолитный
`pytest tests/unit --cov` на этой машине падает с OOM, то есть coverage
не пересчитывался целиком ни разу.

## Как измерено

Монолитный запуск невозможен — kernel OOM-kill'ит xdist-воркер:

```
Out of memory: Killed process 1390537 ([pytest-xdist r) total-vm:15573168kB,
anon-rss:7265276kB
```

Поэтому применено шардирование, уже использованное для полного suite:

- 33 группы по ~700 тестов, каждая отдельно: `pytest -q -p no:randomly -n 2 --dist loadfile`;
- накопление данных — `--cov-append`, чтобы каждая группа **добавляла** к
  существующему `.coverage`, а не заменяла его. Проверено: группа 0 = 13 %,
  группы 0+1 = 15 %, финал = 74 %;
- замер по ходу: 28 % (9/33) → 40 % (13/33) → 48 % (18/33) → 56 % (21/33)
  → 65 % (26/33) → 68 % (28/33) → **74 %** (33/33).

## Оговорка к точности

Группа `grp_031` (≈700 тестов, крупнейшая) при instrumented-прогоне
не уложилась в таймаут 1800 с (`rc=124`), а её повторный прогон потерял
xdist-воркер по памяти (`node down: Not properly terminated`). Её данные
попали в `.coverage` частично — из первого прогона, до таймаута.

Итог **74 % является нижней границей**: полный прогон этой группы дал бы
число не ниже, поскольку недостающие тесты могут только добавить покрытие.
Ни в одном из прогонов `FAILED`-строк не появилось (0 в обоих), то есть
на измерение это не повлияло.

## Попутная правка конфигурации

`coverage report` падал с `No source for code:
'src/backend/_test_dsl_proc_gate_violation.py'`. Причина: гейт-тест
`tests/unit/tools/test_dsl_processors_imports_gate.py` создаёт временный
файл прямо в `src/backend/` и удаляет его в `finally`. Coverage успевала
измерить файл, но к моменту отчёта его на диске уже не было.

Добавлен `omit = ["src/**/_test_*.py"]` в **обе** секции — `[tool.coverage.run]`
(чтобы не собирать) и `[tool.coverage.report]` (потому что filtering
применяется и на этапе отчёта, иначе уже собранный `.coverage` сохраняет
запись об удалённом файле и отчёт падает с exit 1). После правки
`coverage report` завершается с `exit=0`.

Это не код проекта, а транзиентный артефакт теста, поэтому исключение
корректно и ничего не ослабляет.

## Замечание по инструменту

`tools/coverage/breakdown_by_layer.py` классифицирует все 2 428 файлов как
`other` — его правило слоёв не соответствует текущей раскладке каталогов
(в частности, не отделяет `src/frontend` и `src/testkit`). Покрытие по слоям
этим инструментом не получить; разбивка требует отдельной правки, не входящей
в объём текущей задачи.
