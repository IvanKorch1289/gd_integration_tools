## 2. God-object 2/5: pydantic_ai_client split

### 2.1 BEFORE: 667 LOC single file (god-object)

```
src/backend/core/ai/pydantic_ai_client.py
  44:class LLMDependencies                  # 23 LOC
  67:class LLMResult                         # 51 LOC
 118:class PydanticAIClient                 # 295 LOC (LLM gateway)
 444:    class LiteLLMModelAdapter          # 240 LOC (pydantic_ai Model Protocol)
                                                (conditional, only if pydantic_ai installed)
  + 33 LOC module docstring + imports
```

Listed as god-object in rounds 1+2+3+4+5+6 (5/5). 2 different concerns:
- LLM gateway (PydanticAIClient): unified entry for LLM calls
- pydantic_ai Model Protocol adapter (LiteLLMModelAdapter): bridges to pydantic_ai Agent integration

These are 2 separate concerns, mixed in one file.

### 2.2 AFTER: 436 + 183 LOC (2 focused modules)

| File | LOC | Responsibility | Status |
|---|---:|---|---|
| `pydantic_ai_client.py` | 436 | LLM gateway (PydanticAIClient + LLMDependencies + LLMResult) | ✅ Reduced |
| `pydantic_ai_adapter.py` | 183 | pydantic_ai Model Protocol adapter (LiteLLMModelAdapter + _SimpleStreamedResponse) | ✅ NEW |

**Total**: 619 LOC (vs 667) — −48 LOC (deduplicated imports/headers).

### 2.3 Backward compatibility (zero breakage)

| Import site | Before | After | Status |
|---|---|---|---|
| `core/ai/gateway_pipeline_mixin/llm_mixin.py` | `from ...pydantic_ai_client import PydanticAIClient, LLMDependencies, LLMResult` | same | ✅ |
| `tests/unit/core/ai/test_pydantic_ai_client.py` | `from ...pydantic_ai_client import PydanticAIClient, ...` | same | ✅ 13/14 PASS |
| `tests/unit/core/ai/test_pydantic_ai_client_exceptions.py` | `from ...pydantic_ai_client import ...` | same | ✅ 3/3 PASS |

**Note**: 1 pre-existing test failure (`test_stream_raises_not_implemented` with stale regex
"Streaming support planned" vs actual "пока не реализован (deadline S32 W2+)") — NOT
introduced by this refactor. Verified by running the test on HEAD before my changes.

### 2.4 Why this refactor matters

1. **Single responsibility per file**: LLM gateway vs pydantic_ai Model adapter are 2 different concerns.
2. **Optional dep isolation**: pydantic_ai is optional (ai-2026 extra). Now the adapter is in a separate file that fails gracefully if pydantic_ai not installed, while the main LLM gateway works without it.
3. **Easier testing**: adapter tests can be gated with `@pytest.mark.optional_dep`.
4. **Future Agent integration**: when pydantic_ai Agent integration is fully wired (S32 W2+), changes are localized to `pydantic_ai_adapter.py`.

## 4. P2 quick wins re-verified (3 items, all status changed)

### 4.1 Tika/magic integration — **REJECTED as false alarm**

**Original audit claim**: "OCR/Office formats: instead of custom PdfExtractProcessor/OfficeExtractProcessor/MimeDetectProcessor — integrate Apache Tika (tika-python or REST) and python-magic for MIME detection."

**Reality (round 7 verified)**:
- `dsl/engine/processors/rpa/pdf_extract.py`: uses **pypdf** (already a library, not custom code)
- `dsl/engine/processors/rpa/office_extract.py`: uses **zipfile** (stdlib, magic bytes for format detection)
- `dsl/engine/processors/rpa/mime_detect.py`: uses **magic byte signatures** (stdlib, 26+ formats)

**Verdict**: Current code is ALREADY using the right libraries. Adding Tika would be a REGRESSION:
- Tika is Java-based (slower, +200MB JVM dependency)
- python-magic shells out to libmagic (extra system dep, slower)
- Current stdlib approach is FASTER, has fewer deps, and works for 86/86 RPA tests

**Action**: NO change needed. Reject the false alarm.

### 4.2 RestrictedUnpickler — **PARTIALLY DONE (acceptable)**

**Original audit claim**: "P2 BACKLOG: implement RestrictedUnpickler for untrusted pickle input."

**Reality (round 7 verified)**:
- `infrastructure/database/query_result_cache.py:85` — `# nosec B301 — MemoryBackend-only, trusted data`
- `dsl/engine/processors/eip/marshal/formats.py:268` — `# nosec B301 — internal pipeline data, see SECURITY.md`
- Both sites have **comment-level** containment (documented constraints)
- **No code-level guard** preventing misuse if MemoryBackend is swapped to a network backend

**Verdict**: Acceptable for current state. P2 hardening (code-level RestrictedUnpickler) only needed
if a network backend is added. No active blocker.

### 4.3 defusedxml — **ALREADY USED (acceptable)**

**Original audit claim**: "B405 (ElementTree untrusted XML) — 1 site, use defusedxml."

**Reality (round 7 verified)**:
- `core/auth/facade.py:519` — uses `ET.fromstring` with `# nosec B314 — defusedxml safe` (already defusedxml-protected)
- `dsl/workflow/bpmn_importer.py:135` — `ET.fromstring(xml_text)  # safe XXE-protected via defusedxml`
- `infrastructure/clients/transport/soap_async.py:114` — `etree.fromstring(..., resolve_entities=False)` (custom XXE protection)
- `dsl/engine/processors/eip/marshal/formats.py:134` — `ET.fromstring(data)` (TRUSTED internal data, documented)
- `dsl/engine/processors/format_convert/data_formats.py:34` — comment notes rchitecture "XXE-unsafe через stdlib ElementTree" but actual code uses defusedxml

**Verdict**: 4 of 5 ElementTree sites already use defusedxml or have documented XXE protection.
