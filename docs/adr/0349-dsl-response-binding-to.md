# ADR-0349 — Response-binding (`to:`) в DSL-роутах

* Статус: Draft (на согласование)
* Дата: 2026-10-09
* Затрагивает: `src/backend/dsl/engine/pipeline.py`, `src/backend/dsl/yaml_loader/build.py`, `src/backend/dsl/builders/base/fluent_mixin.py`, протокольные фасады
* Связан с: CLAUDE.md §«DSL Dual-Mode Principle», ADR-0348, `artifacts/current_audit/AUDIT_2026-10-06_runtime_wiring.md`

## Контекст

Блоки `to:` были молча удалены из `routes/*/*.dsl.yaml` (коммит `907c04b63`),
потому что `_build_pipeline()` их не читает. Молча — вот что важно: YAML
валидировался, роут загружался, но объявленный response-binding не выполнялся
и никто об этом не сообщал.

Два независимых следствия расходятся в API:

| Слой | Что есть | Следствие |
|---|---|---|
| YAML | ключ `to` не читается `_build_pipeline()` | молчаливое игнорирование |
| Python | `RouteBuilder.to(...)` — это алиас `process(processor)` | `.to("response", code=..., body=...)` не существует |

То есть response-binding отсутствует в **обеих** модах, причём в Python-режиме
метод с ожидаемым именем существует и делает совершенно другое.

## Установленные факты (HEAD `6498eb1e3`)

Механизм на стороне движка **уже есть**:

- `Exchange.out_message` (`engine/exchange.py:146`) — поле для результата;
- `ExecutionEngine._finalize()` (`execution_engine.py:215`) — если
  `out_message is None`, экшен завершается телом входного сообщения
  (эхо); если задан — статус `completed`, тело берётся из `out_message.body`.

Но потребители `out_message` ограничены:

```
services/dsl_portal/builder_facade.py:280     — читает out_message.body
entrypoints/api/v1/endpoints/dsl_console.py    — читает out_message.body
dsl/cli/debug.py                               — читает out_message
```

Основной путь обслуживания протоколов (auto-registration через `@service_dsl`
и `service.toml`, R-V15-3) через `builder_facade` **не проходит** и
`out_message` не читает.

## Проблема

Объявить `to:` публичным контрактом в текущем виде нельзя: роут, объявивший
`to: {response: {code: 201, body: ${...}}}` в консоли отработал бы корректно, а
по REST/gRPC/WS/MQ вернул бы эхо входного сообщения. Ровно тот режим молчаливого
отказа, который и вынудил удалить блоки из роутов.

## Рассмотренные варианты

### Вариант A. Объявить `to:` только для DSL-консоли и portal

Добавить ключ в YAML и метод в builder, документировав ограничение: binding
применяется в dry-run/console, а не в протокольном обслуживании.

- **Плюсы:** закрывает наблюдаемый дефицит без изменения протокольных путей;
  ровно совпадает с тем, что уже умеет текущий движок.
- **Минусы:** один DSL с двумя разными семантиками ответа. Тот же YAML,
  попавший в прод через REST, снова будет игнорировать `to:` — то есть
  воспроизводит исходную проблему в новой форме.

### Вариант B. Сначала научить протокольные фасады читать `out_message`

Во всех точках, где тело ответа строится из exchange, проверять `out_message`
и при его наличии отдавать `out_message.body` + статус/заголовки из него.
Только после этого объявлять `to:`.

- **Плюсы:** единственная семантика DSL; `to:` становится настоящим контрактом.
- **Минусы:** затрагивает все авто-регистрируемые протоколы (REST, SOAP, XML,
  gRPC, GraphQL, MQ, WS, SSE, MCP, MQTT) — большой объём и риск регрессий в
  транспортном слое; статус-коды и заголовки требуют согласования на каждое
  семейство протоколов.
- **Риск:** промежуточное состояние «`to:` в YAML есть, но игнорируется»
  снова возможно, если порядок шагов нарушить.

### Вариант C. Не вводить `to:`, расширить `set_property`/processors

Ответ формируется процессорами (`transform`, `template_engine`), а наружу
отдаётся как есть. Отдельного binding-контракта нет.

- **Плюсы:** ноль изменений в публичном DSL; нет нового молчаливого отказа.
- **Минусы:** не отвечает на запрос «роут должен вернуть другой код/тело» —
  композиция только в DSL-шагах, статус ответа невыразим.

### Вариант D. Ввести `to:` с обязательной вализацией

Ключ `to:` появляется в схеме, но при загрузке роута, если `to` задан и
протокольный путь его не поддерживает, роут **не регистрируется** с явной
ошибкой.

- **Плюсы:** fail-fast вместо молчаливого игнорирования — согласуется с
  принципом fail-closed, уже принятым в проекте.
- **Минусы:** несовместимо с любым существующим роутом, где `to:` остался
  в yaml; требует миграции.

## Рекомендация

**B → A, с промежуточной фиксацией D.**

1. Сначала (B) протокольные фасады учатся читать `out_message`. До этого
   шага `to:` в схему не добавляется.
2. Затем (A) появляется сам ключ/метод.
3. До момента, когда поддержка есть во всех протоколах, загрузчик (D)
   отвергает `to:` для тех путей, которые его ещё не исполняют, — с явным
   сообщением, а не с игнорированием.

Вариант A в одиночку **не рекомендуется**: он формализует расхождение
семантик между консолью и протоколами и делает исходный молчаливый отказ
воспроизводимым. Вариант C оставляет дефицит, но это честный статус quo.

## Критерий приёмки

- [ ] Определено, какие протоколы входят в первый срез поддержки `to:`.
- [ ] Каждый такой протоколный фасад покрыт тестом, возвращающим
      `out_message.body`, а не эхо входа.
- [ ] Ключ `to:` появляется в JSON-схеме DSL **после** (B).
- [ ] Загрузчик отвергает `to:` явно там, где он не поддержан (D).
- [ ] Ни один существующий `routes/*/*.dsl.yaml` не содержит `to:` —
      инвариант проверяется тестом, чтобы блок не вернулся молча.
