# ADR-0455 — Автоматизация инфраструктурных действий (keypair JWKS, роль BYPASSRLS)

* Статус: Accepted (2026-11-17, волна 33)
* Cycle: 189 (волна 33)
* Связан с: ADR-0441 (инфра-чек-лист), ADR-0364 (секреты через Vault), ADR-0383 (RLS-политика)
* Затрагивает: `tools/generate_jwks_keypair.py`, `ops/sql/bypassrls_role.sql`, `docs/ops/infra-release-checklist.md`

## Контекст

Шесть инфраструктурных пунктов из чек-листа (ADR-0441) требовали ручных
действий: keypair для JWKS (RS256), роль БД с `BYPASSRLS`, OpenWebUI,
ClickHouse в проде, JupyterHub, `replica_dsn`. Кодовая часть каждого была
готова, но шаги не были формализованы → их невозможно было выполнить
воспроизводимо.

## Решение

Автоматизируемая часть переносится в репозиторий (остальное — за владельцем,
команды в чек-листе):

1. **`tools/generate_jwks_keypair.py`** — генерация RSA-2048 keypair для
   RS256: приватный PEM (0600) + JWKS-документ (публичный). Защиты:
   отказ записывать ключи внутрь репозитория, в stdout — только пути и
   отпечаток; приватный ключ → secret-менеджер, JWKS → ConfigMap/Secret.
2. **`ops/sql/bypassrls_role.sql`** — роль `snapshot_service`
   (`NOLOGIN BYPASSRLS`, только SELECT на таблицы снимка) для
   межtenant-снапшота; роль не выдаётся приложению.

## Уточнение волны 33 (2026-11-16): артефакты доведены до применимости

Независимая проверка показала, что первая версия артефактов не работала так,
как задокументировано:

* **генератор**: `--out-dir <корень репозитория>` не отклонялся (корень не
  является собственным parent'ом) → приватный ключ писался в рабочее дерево;
  повторный прогон (ротация ключа) падал на read-only `jwks.json` (0444);
* **SQL-роль**: команда из шапки файла падала (не передавался `snapshots_db`);
  гранты не покрывали таблицы снимка (`certs`, `cert_history`); имя роли
  расходилось с каноном `docs/ops/snapshot-bypassrls-role.md`;
* **чек-лист**: env-имена `JWT_JWKS_URL` / `JWT_ALGORITHM` /
  `DATABASE_REPLICA_DSN` не существуют (в коде префиксы `SEC_` / `DB_`);
  ссылка на «сервис `clickhouse` в `docker-compose.prod.yml`» — такого
  сервиса нет; JWKS-бэкенд указан в `auth_selector.py`, а он собирается в
  `core/di/providers/auth.py`; не указано требование `https` для `jwks_url`.

Исправлено и **проверено прогонами**: SQL применён на временном PostgreSQL
16.15 (роль, гранты, идемпотентность, read-only через `SET ROLE`); генератор
проверен на отказ «внутри репозитория» и на повторный запуск (4 теста).

## Последствия

* keypair и роль БД воспроизводимы по команде, а не по памяти оператора;
* риск «секрет в репозитории» закрыт проверкой в генераторе и тестом;
* OpenWebUI / ClickHouse / JupyterHub остаются инфраструктурными действиями:
  для них нет кода, который можно выполнить в этом репозитории (нужен образ,
  сеть и развёртывание) — команды и требования в чек-листе;
* за владельцем остаются: keypair+секрет-менеджер, JWKS-сервис (https),
  применение роли БД и DSN снапшота, внешний ClickHouse, OpenWebUI,
  JupyterHub, `DB_REPLICA_DSN`.
