# ADR-0448 — ORM-ветка tenant-изоляции: fail-closed без tenant (вариант А)

* Статус: Accepted (вариант **А** — решение владельца 2026-11-16)
* Cycle: 188 (волны 31–32)
* Связан с: ADR-0417 (tenant-guard: fail-closed без tenant), ADR-0428 (UNION/CTE), ADR-0383 (RLS)
* Затрагивается: `src/backend/core/tenancy/sqlalchemy_filter.py` (`_filter_by_tenant`)

## Контекст

Проверка (независимый агент, безопасность) подтвердила: **ORM-ветка**
tenant-изоляции не fail-closed. В `_filter_by_tenant` при пустом
tenant-контексте выполняется `return` — SELECT/UPDATE/DELETE идут **без**
tenant-предиката. Второй эшелон (RLS) есть только в PostgreSQL
(`set_tenant_scope`), поэтому на SQLite/Oracle/MySQL-профилях выборка читала
строки всех tenant'ов.

DSL-путь при этом fail-closed (`databasequeryprocessor`, ADR-0417) ✓, и внешний
контур явно исключён (`is_main_scope`) ✓ — дыра именно в «сыром» ORM-доступе.

## Решение (вариант А, принят владельцем 2026-11-16)

Принят **вариант А**: три явных состояния tenant-скоупа.

| Состояние | Поведение ORM-фильтра | Кто использует |
|---|---|---|
| контекста нет | кросс-tenant без фильтра (дефолт = платформенный scope) | фоновые/служебные потоки вне tenant-контекста |
| `tenant_id = _system` (`SYSTEM_TENANT_ID`) | кросс-tenant без фильтра | явная пометка платформенного scope |
| `tenant_id = ""` | **fail-closed**: `TenantIsolationError` для tenant-aware сущностей | явный «без tenant'а» |
| реальный tenant | фильтр `tenant_id = <tenant>` | пользовательский контур |

Инвариант: пользовательский контур **всегда** с tenant-контекстом (его
выставляет auth-middleware), поэтому кросс-tenant поведение по умолчанию
достижимо только из внутреннего кода, а не из пользовательского ввода.
Системный scope сделан явным (`system_tenant_context()`), чтобы служебные
потоки не зависели от «пустого» tenant'а.

Раньше ORM-ветка при отсутствии контекста выполняла SELECT/UPDATE/DELETE без
предиката (RLS есть только в PostgreSQL) — на SQLite/Oracle/MySQL это давало
чтение строк всех tenant'ов.

## Последствия

* Кросс-tenant чтение в пользовательском контуре закрыто: там контекст всегда
  есть, а явный пустой tenant → отказ;
* служебные потоки (планировщик, аудит-версионирование, репозитории) работают
  как раньше (контекста нет → платформенный scope);
* миграция внутренних потоков на явный `system_tenant_context()` — чистое
  улучшение читаемости (в отдельной волне, без изменения поведения).

## Уточнение волны 33 (2026-11-16)

* **UNION/CTE в fail-closed ветке.** Независимая проверка (волна 33)
  обнаружила обход: `_tenant_aware_entities()` смотрела только на верхний
  уровень statement'а, а у `CompoundSelect` (UNION) и CTE-источников нет ни
  `column_descriptions`, ни `entity_description` → при пустом tenant запрос
  проходил без предиката. Исправлено: добавлен обход вложенных statement'ов
  (ветви UNION + определения CTE) и два регрессионных теста
  (`tests/unit/core/tenancy/test_tenant_filter_orm_dml.py`).
* **Документация приведена в соответствие.** Заголовок ADR и строка в
  `docs/adr/INDEX.md` больше не утверждают «решение отложено» (решение
  принято, вариант А); docstring `SYSTEM_TENANT_ID` в
  `core/tenancy/__init__.py` теперь описывает фактическое поведение:
  отсутствие контекста — платформенный scope, fail-closed — только явный
  пустой tenant.
* **Остаётся на владельца.** Миграция внутренних потоков на явный
  `system_tenant_context()` (сейчас функция используется только в тестах) и
  сверка платформенного scope по бэкендам: на PostgreSQL с включённым RLS
  «нет контекста» даёт 0 строк вместо кросс-tenant чтения — поведение не
  бэкенд-инвариантно и требует решения владельца.
