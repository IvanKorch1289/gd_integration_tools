## 🔴 Блокеры

1. `src/backend/core/tenancy/context.py:127` — **`TenantContext.to_tenant()`
   подменял `principal_id=None` на системного principal'а**
   (`principal=self.principal_id or SYSTEM_TENANT_ID`). Контекст без
   principal'а превращался в «действует системный principal» → проверка
   прав, требующая principal'а, выдала бы доступ вместо отказа
   (fail-open на границе доверия). Хотя `to_tenant()` сегодня не имеет
   production-call-sites, это ловушка для следующего вызывающего.
   **Исправлено:** подмена убрана, `CapabilityTenant.principal` сделан
   опциональным (`str | None = None`), добавлены 2 регресс-теста
   (`test_to_tenant_does_not_substitute_system_principal`).

## ❓ Вопросы (требуют решения владельца)

1. **Изменение enforcement.** Привязка caller-namespace в последовательном
   пути (ADR-0430) делает декларации роутов на ресурсы действующими: роут,
   объявивший `net.outbound`/`storage.*`/`cache.*`/`db.*`, получает доступ
   в пределах своего scope. Инвариант «`GRANT→DENY` невозможен» доказан
   (тест), но **scope'ы 7 роутов стоит подтвердить перед раскаткой**.
2. **Scope vs host-glob.** `health_proxy_demo` и `composition_demo`
   объявляют `net.outbound` со scope вида `https://localhost:9000:internal`,
   а рантайм-гейт сверяет **host** (dot_glob). Сейчас `proxy` использует
   ad-hoc клиент без `capability_check` → не проявляется; при появлении
   проверки будет `DENY`.
3. **`Cache-Control: public` на аутентифицированных ответах** (pre-existing,
   вне P2-5): shared cache явно допущен к хранению tenant-специфичного
   контента, `Vary` отсутствует. ETag-фикс смягчает, но не решает.
4. **Стриминговая регрессия HTTP-цепочки** (pre-existing): стриминговый
   GET-ответ обрезается до первого чанка полной цепочкой middleware;
   поведение одинаково до и после волны 36, локализовать не удалось
   (bisect-пробы зависают под ASGI-транспортом).
5. **Кнопка выхода в портале:** `logout()` теперь чистит API-кэш, но в UI
   кнопки выхода нет → фикс не срабатывает, пока её не добавят.
6. **Библиотечные правки** (ruamel.yaml в runtime, удаление
   `grpc-interceptor`, объявление `requests`, SHA-пиннинг actions,
   `pytest-xdist --dist worksteal`, одна версия `tenacity`) — почти все
   требуют изменения lock-файла, что по правилам проекта (Sprint 36)
   делается только с явного согласования.

## ✅ Что сделано хорошо

- **Fail-safe по умолчанию.** Привязка namespace выполняется только для
  роутов с декларациями; гейт владения actions fail-closed; нормализация
  tenant-контекста бросает `TypeError` вместо «тихого» tenant-less.
- **Регресс-тесты ловят дефект, а не его отсутствие.** ETag: на старом
  порядке middleware — 5 красных из 8; payload_model: 4 красных из 9;
  namespace: 2 красных из 6. Это и есть проверка качества фикса.
- **Инвариант вместо надежды.** «`GRANT→DENY` невозможен» зафиксирован
  тестом `test_platform_namespaces_declare_no_resource_capabilities` — не
  комментарием в ADR.
- **Новый гейт не съедает бюджет блокирующих.** Шаг владения actions
  добавлен в `lint.yml` последним (после всех блокирующих гейтов) —
  ошибка волны 35, когда мутационный гейт стоял в середине job'а и
  блокировал ~20 гейтов после себя.
- **Дед-код удалён, а не закомментирован.** Мёртвый модуль регистрации
  actions с конфликтующим payload_model удалён вместе со своими тестами;
  упоминания в документации переформулированы, исторические отчёты —
  в baseline.
