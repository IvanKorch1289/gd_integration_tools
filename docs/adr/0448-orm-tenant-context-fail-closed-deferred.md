# ADR-0448 — ORM-ветка tenant-изоляции: fail-closed без tenant (решение отложено)

* Статус: **Proposed** (дефект подтверждён, внедрение отложено — 2026-11-10)
* Cycle: 188 (волны 31–32)
* Связан с: ADR-0417 (tenant-guard: fail-closed без tenant), ADR-0428 (UNION/CTE), ADR-0383 (RLS)
* Затрагивается: `src/backend/core/tenancy/sqlalchemy_filter.py` (`_filter_by_tenant`)

## Контекст

Проверка (независимый агент, безопасность) подтвердила: **ORM-ветка**
tenant-изоляции не fail-closed. В `_filter_by_tenant` при пустом
tenant-контексте выполняется `return` — SELECT/UPDATE/DELETE идут **без**
tenant-предиката. Второй эшелон (RLS) есть только в PostgreSQL
(`set_tenant_scope`), поэтому на SQLite/Oracle/MySQL-профилях выборка читала
строки всех tenant'ов.

DSL-путь при этом fail-closed (`databasequeryprocessor`, ADR-0417) ✓, и внешний
контур явно исключён (`is_main_scope`) ✓ — дыра именно в «сыром» ORM-доступе.

## Решение (отложено)

Пробный fail-closed (`TenantIsolationError` при отсутствии tenant'а для
tenant-aware сущностей) **не принимается в этой волне**: он ломает 42
платформенных теста — внутренние потоки планировщика (scheduler, audit
versioning, rule-engine repository) обращаются к tenant-aware таблицам без
tenant-контекста (системные/служебные выборки).

Корректное решение требует выбора между:

* **(А)** системный tenant по умолчанию (`SYSTEM_TENANT_ID`) — запросы
  служебных потоков ограничены системным tenant'ом, чужие данные не читаются;
* **(Б)** явная привязка tenant'а во всех внутренних потоках (scheduler,
  audit-versioning, repositories) + fail-closed в фильтре.

Вариант (Б) точнее по смыслу, но затрагивает десятки мест и требует
отдельной волны с регрессией каждого потока. Вариант (А) — меньше риска,
но «молча сужает» выборки служебных потоков.

**До решения:** дефект зафиксирован как critical в реестре owner-задач
(OWNER_TASKS §17) и в роевом отчёте; изменение поведения откачено
(commit `83aafa11a`), чтобы не сломать платформу.

## Последствия

* Известный риск: «сырой» ORM-доступ без tenant-контекста читает данные всех
  tenant'ов вне PostgreSQL. Эксплуатация требует прямого доступа к ORM в
  прикладном коде (не через DSL/фасады) — то есть внутреннего кода, а не
  пользовательского ввода.
* Требуется решение владельца: вариант (А) или (Б).
