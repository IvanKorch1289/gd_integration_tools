## Подтверждение для #1 (`admin_plugins.py`)

```
$ find . -name "admin_plugins*" -not -path "./.git/*" -not -path "*/__pycache__/*"
./src/backend/entrypoints/api/v1/endpoints/admin_plugins.py
./src/backend/entrypoints/api/v1/endpoints/admin_plugins       ← каталог
```

`routers.py:57` импортирует `admin_plugins`:
```
from src.backend.entrypoints.api.v1.endpoints.admin_plugins import (...)
```

CPython: при наличии `__init__.py` импорт `admin_plugins` всегда выбирает пакет (PEP 328 / import system). Файл `admin_plugins.py` (556 LOC) физически не достижим ни одним `import`.

**Чтобы удалить безопасно**, по правилу проекта:
1. Не делать этого без явного подтверждения (CLAUDE.md «запрещено удалять файлы без явного подтверждения»).
2. Перед удалением выполнить `find -name "admin_plugins.py"` → удалить → `make ruff format-check && make check-layers && make check-docstrings && make security`.
3. Сделать это пачкой (отдельный коммит только на удаление).

## Почему реестр `deadcode_candidates.json` ошибочно включает #2 и #3

Сам `deadcode_verify.py` предупреждает (в его `IMPORTANT` шапке):
> «Этот инструмент даёт ЛОЖНЫЕ срабатывания на автономных CLI-инструментах.
> Критерий «нет production-импортёров» неприменим к точкам входа».

Список с самого начала различает эти случаи в `note` полях:
- generate_api_client.py: «0 импортёров и 0 вызывающих; не упомянут в Makefile/CI»
- classify_object_authorization.py: «0 импортёров; одноразовый анализатор»

Но `verify` без `note`-агентации и без регрессионного теста на поведение
помечает их как «мёртвые». Правильная проверка — `ripgrep без .py` + ручная
верификация запуска (для CLI).
