# ADR-0431 — Идемпотентность внешних вызовов и единая семантика компенсации

* Статус: Accepted (2026-11-09, волна 28)
* Cycle: 187 (волна 28)
* Связан с: ADR-0394 (event log workflow), ADR-0403/0408 (SLA/DLQ), ADR-0414 (step-audit)
* Затрагивает:
  - `src/backend/infrastructure/workflow/pg_runner_internals/step_keys.py` (новый: общий `idempotency_key`),
  - `src/backend/infrastructure/workflow/executor/sequential_mixin.py` (проброс ключа в Exchange),
  - `src/backend/dsl/engine/processors/components/httpcallprocessor.py` (заголовок `Idempotency-Key`),
  - `src/backend/infrastructure/workflow/executor/compensating.py` (индекс компенсации)

---

## Контекст

1. **Ключ идемпотентности не доходил до внешнего вызова.** Runner вычислял
   `idempotency_key(instance, step, attempt)` и клал его в **событие**
   event log'а, но payload активности содержал только данные шага. Падение
   worker'а после успешного внешнего вызова → повтор шага → возможен дубликат
   платежа/события на стороне получателя.
2. **Компенсация откатывала разные шаги в разных движках.** Temporal-путь
   считает позиционный индекс компенсации по списку **выполненных** forward-шагов,
   pg-runner — по списку **всех** forward-шагов. При частичном падении цепочки
   (forward `[A, B, C]`, выполнены `[A, C]`) движки откатывали разные шаги,
   хотя `compensating.py` заявлял «семантика выровнена с Temporal-путём».

---

## Решение

1. Функция ключа вынесена в общий модуль (`pg_runner_internals/step_keys.py`),
   чтобы runner и executor использовали одно определение.
2. Executor вычисляет ключ шага и кладёт его в **свойства Exchange'а**
   (`idempotency_key`), а не в payload: ключ не должен ломать контракт
   action'ов с запретом лишних полей.
3. `http_call` читает свойство и пробрасывает его получателю заголовком
   `Idempotency-Key` (контракт для получателя: повтор с тем же ключом —
   вернуть исходный результат, не выполнять эффект повторно).
4. Компенсация в pg-runner считает индекс по списку **выполненных** шагов —
   как в Temporal-пути.

---

## Последствия

* Получатель внешнего вызова может отбросить дубликат; для вызовов без
  поддержки заголовка поведение не меняется (ключ доступен в свойствах
  Exchange'а).
* Поведение компенсации выровнено между движками; при частичном падении
  откатываются те же шаги.
* Owner-задачи: (1) распространить заголовок на webhook/MQ-sink и другие
  внешние вызовы; (2) описать контракт идемпотентности в документации
  workflow; (3) решить, какой результат возвращать получателю при повторе.
