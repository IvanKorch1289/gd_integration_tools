# Профиль потребления ресурсов и предложения по оптимизации (2026-11-23)

Документ содержит **измерения**, а не оценки: каждое число получено командой,
приведённой в разделе 1. Предложения в разделе 3 — с ожидаемым эффектом и
критерием приёмки; ожидаемые эффекты помечены как оценка, если не подтверждены
замером.

Контекст: волна исправлений HTTP-контрактов (2026-11-20) закрыла функциональные
дефекты; этот документ — следующий срез: **сколько ресурсов приложение
занимает и где их тратит без нужды**.

## 1. Методика и воспроизводимость

| Что | Как измерено |
|---|---|
| Старт приложения | `python -c "from src.backend.plugins.composition.app_factory import create_app; create_app()"` с замером `time.perf_counter()` и `resource.getrusage(RUSAGE_SELF).ru_maxrss` |
| Профиль старта | `cProfile` вокруг `create_app()`, сортировка по `cumulative` |
| Путь импорта presidio | подмена `builtins.__import__` с трассировкой `traceback.extract_stack()` при первом импорте `presidio_analyzer` |
| Per-request overhead | `starlette.testclient.TestClient`, 300 запросов к тривиальному `JSONResponse`, сравнение «пусто» vs «полная цепочка middleware» |
| Вклад маскирования | тот же клиент, 5 МБ JSON, замер с отключением `data_masking` / `pii_masking_response` по одному |
| Образ | `docker image inspect --format '{{.Size}}'`, `docker history`, `du` внутри контейнера |
| Ограничение памяти | `docker run --memory=1g --memory-swap=1g` |

Ограничения измерений: в контейнере прод-образа `create_app()` не измерялся —
настройки валидируются eagerly и требуют секретов из `.env` (читать нельзя по
правилам проекта); поэтому для контейнера приведены отдельные замеры
(импорт presidio, геометрия образа), а для полного старта — локальные числа с
явной пометкой среды.

## 2. Измеренный профиль

### 2.1 Старт

| Метрика | Локально (dev-venv) | В прод-образе |
|---|---|---|
| Интерпретатор | 15 МБ RSS | — |
| `import app_factory` | 2.7–3.5 с, RSS 234 МБ | требует секретов, не измерено |
| `create_app()` | **7.8 с**, RSS **1182 МБ** | не измерено (см. ограничение) |
| `import presidio_analyzer` | 7.2 с, RSS **918 МБ**, 5608 модулей | **4.2 с, RSS 107 МБ**, 1308 модулей |
| `APP_PROFILE=dev_light` | 6.3 с, RSS 1166 МБ | — |
| Middleware в цепочке | 37 (30 после отключения инфраструктурных) | те же |
| Маршрутов после `create_app()` | 162 (132 авто-регистрацией + 16 legacy-алиасов) | те же |

**Разница 918 МБ против 107 МБ** — это dev-only нагрузка: в dev-venv стоят
spacy-модели и полный AI-стек (`torch` 1.15 ГБ + `nvidia-*` 3.2 ГБ +
`triton` 0.9 ГБ = **5.2 ГБ из 9.3 ГБ venv**). В прод-образ их нет, поэтому
цифра 1182 МБ — свойство dev-среды, а не прода. **Но время импорта presidio
(4.2 с) — свойство прода**, и оно платится на каждом старте.

### 2.2 Кто платит за старт

Профиль `create_app()` (19.4 с под cProfile) даёт однозначный ответ:

```
16.25 с  app_factory._configure_auto_registered_actions
 15.99 с  dsl/commands/setup/orchestrator.py:register_action_handlers
  15.95 с  dsl/commands/setup/registers_domains.py:_register_servicedsl_auto_register
   15.95 с dsl/service_dsl.py:scan_and_register_actions
    14.61 с services/ai/pii/recognizers/__init__.py
     14.59 с presidio_analyzer  ← импорт Presidio на старте
```

Скан `@register_action` обходит **392 модуля** пакета `src.backend.services` и
регистрирует **0 действий** (в production-коде нет ни одного
`@register_action`; декоратор встречается только в docstring и в одном тесте).
Логи приложения это подтверждают: `Auto-registered 0 actions from @register_action
decorators`.

То есть ~14.6 с старта (локально) / ~4.2 с (прод-образ) тратятся на импорт
тяжёлой зависимости, чтобы не найти ничего.

## 3. Предложения (по убыванию эффекта)

> Статус на 2026-11-23: **P1 и P2 реализованы** (см. §3.1), **P5 переработан**
> (гейт стал машинно-независимым и вскрыл реальную регрессию → P8), P3–P4 и
> P6–P7 — предложения к решению владельца.

### 3.1 Реализовано в этой волне

| Предложение | Было | Стало | Проверка |
|---|---|---|---|
| **P1** скан `@register_action` под флагом `FEATURE_DSL_AUTO_SCAN_ACTIONS` (default-OFF) | `create_app()` **7.82 с**, RSS **1182 МБ**, presidio загружен | `create_app()` **5.99 с**, RSS **304 МБ** (−74 %), presidio **не импортируется** | 132 actions на месте; 4 новых теста (`tests/unit/dsl/test_auto_scan_flag.py`); dsl-регрессия 5605 passed; entrypoints 1839 passed |
| **P2** права на `COPY --chmod=750` вместо `chmod -R` после копирования | образ **2.42 ГБ** (дублирующий слой 1.15 ГБ поверх venv-слоя 1.15 ГБ) | образ **1.23 ГБ** (−49 %) | реальная сборка образа + проверка запуска от `appuser` (права 750, `manage.py` работает); механизм дублирования доказан на минимальном образе (60 МБ → дубликат 60 МБ против `--chmod` без дубликата) |

Детали P1: скан обходил 392 модуля `src.backend.services` ради поиска
`@register_action`-декораторов, которых в production-коде нет, и тянул
`presidio_analyzer` (4.2 с в прод-образе). Флаг выключен по умолчанию;
наблюдаемый результат (множество зарегистрированных actions) не изменился —
это закреплено тестом на равенство при включённом и выключенном флаге.

Детали P2: `chmod -R 750 /app` меняет метаданные каждого файла, поэтому
Docker копирует предыдущий слой заново — образ раздувался вдвое. Перенос прав
в `COPY --chmod=750` убирает дубликат; отдельным `RUN` остаётся только
`chmod 750 /app` (один каталог) и снятие setuid-битов с системных файлов.

### 3.2 Остальные предложения и найденный дефект

### P1. Не импортировать Presidio на старте — 4.2 с (прод) / 14.6 с (dev)

**Что:** скан `@register_action` (392 модуля, 0 найденных действий) тянет
`services.ai.pii.recognizers` → `presidio_analyzer`.
**Как:** сделать скан opt-in (feature-флаг, дефолт off) либо сузить до пакетов,
где декоратор реально используется; альтернатива — ленивый импорт presidio в
`recognizers/_base.py` (требует рефакторинга базового класса: он наследует
`PatternRecognizer`, поэтому импорт нужен на уровне класса).
**Ожидание:** старт 7.8 → ~3.5 с (dev), ~4.2 → ~1 с (прод).
**Риск:** авто-регистрация actions. Сейчас их 0 → регрессия не ломает
контракт, но тест «число зарегистрированных actions» зафиксировать обязательно.
**Приёмка:** `create_app()` ≤ 3 с (dev) и ≤ 2 с (прод-образ); лог сохраняет
`Auto-registered N actions`; регрессионный тест на N.

### P2. Убрать дублирующий слой образа — −1.15 ГБ (−47 %)

**Что:** `RUN chmod -R 750 /app` после `COPY` дублирует весь venv-слой.
**Как:** перенести права в `COPY --chown=appuser:appuser --chmod=750`; очистку
setuid-битов (`find … chmod a-s`) выполнять в apt-слое, где она не трогает
/app.
**Ожидание:** образ 2.42 → ~1.27 ГБ; быстрее pull в CI и в registry.
**Приёмка:** `docker image inspect` ≤ 1.4 ГБ; приложение стартует (файл
исполняем, права 0750).

### P3. Ограничить маскирование PII крупных ответов — 1.4 с → ~50 мс на 5 МБ

**Что:** `pii_masking_response` разбирает JSON и прогоняет регулярки по всему
телу; флаг включён по умолчанию.
**Как:** (а) лимит размера тела для маскирования (по аналогии с
`max_body_size` в `response_cache`) с passthrough для крупных ответов **и
метрикой пропущенных** — иначе получим тихую дыру в защите; (б) кэш
результата масок по ETag; (в) вынести масокирование в отдельный процесс с
границами CPU/памяти.
**Ожидание:** 5 МБ JSON — 1399 → ~50 мс (без маскирования) либо ~250 мс (с
лимитом и кэшем).
**Риск:** пропуск маскирования — security-регрессия. Поэтому вариант (а)
допустим только вместе с метрикой и явной политикой (fail-closed vs
fail-open) — решение за владельцем безопасности.

### P4. Сократить per-request overhead — часть реализована

**Что:** 37 middleware удваивают latency тривиального эндпоинта.
**Сделано (быстрый путь PII-фильтра):** `pii_filter.redact_for_observability`
прогонял 6 regex'ов по каждой строке лога (33 строки и 174 прохода на
запрос). Пять паттернов из шести требуют цифр, а подстановки цифр не вводят
→ при отсутствии цифр эти пять проходов пропускаются. Замер в одном процессе
с чередованием старой и новой реализации: **3.058 → 2.791 мс/запрос
(экономия 0.268 мс, −8.8 %)**, семантика маскирования не изменилась
(закреплено тестом на равенство эталонному прогону).

**Осталось (предложения):**
* correlation-id: сторонний `asgi_correlation_id` (0.21 мс/запрос, 2 вызова)
  используется обёрткой проекта — реализовать natively, как уже сделано
  для `request_id`;
* проверить thread-hop в `starlette_exporter` (Prometheus) на каждый ответ;
* редкотировать по изменению схемы там, где значения повторяются.

**Приёмка:** цепочка добавляет ≤ 0.4 мс к тривиальному эндпоинту; per-request
профиль не содержит hot-spot'ов > 0.05 мс.

### P5. Починить гейт стартового времени — сейчас красный и нестабильный

**Что:** `startup_time.py` меряет «импорт модуля», но включает старт
интерпретатора и файловый кэш; разброс внутри одного модуля 0.6–1.3 с.
**Как:** мерить только время импорта (вычесть холостой запуск интерпретатора),
увеличить число выборок, перекалибровать baseline на текущем железе; иначе
гейт — шум, который будут отключать.
**Приёмка:** гейт зелёный на трёх прогонах подряд; разброс < 15 %.

### P6. Память тестового прогона — документировать и ограничить

**Что:** единый прогон ~5k тестов → SIGSEGV при 2.6 ГБ свободной RAM; по
пакетам — зелёный.
**Как:** закрепить разбиение по пакетам (как уже сделано для coverage, ADR-0453) в
локальном сценарии `make test`; ограничить xdist-параллелизм по доступной
памяти; зафиксировать требуемую память в README/ADR.
**Приёмка:** `make test` на машине с 4 ГБ RAM завершается без падения ядра.

### P7. Гейт стартового RSS — **реализовано**

Гейт `tools/checks/startup_time.py` теперь измеряет и время, и память:
подпроцесс импортирует все critical-модули и печатает свой максимальный
RSS; сравнение — по тому же baseline-коммиту (отношение), плюс абсолютный
лимит `MAX_STARTUP_RSS_MB = 512`.

Зачем именно RSS-гейт: возврат тяжёлого импорта — это прежде всего
**память**, а время вторично. Именно так в строй вернулся Presidio
(+903 МБ в dev-venv, +107 МБ в прод-образе) — и именно такой дефект
RSS-гейт ловит автоматически.

Текущее состояние (2026-11-23): время — красное (ratio 1.517, регрессия
импорта конфигурации, см. P8), **память — норма** (84.7 МБ против 77.2 МБ
на baseline, ratio 1.098). То есть регрессия P8 — чисто вычислительная,
и это теперь видно прямо из отчёта гейта.

### P8. Разобрать регрессию стартового импорта конфигурации — 1.5–1.9× на модуль

Это не предложение, а **найденный и локализованный дефект** (P5 вскрыл его).
Стартовый импорт конфигурации вырос с 2026-10-15 (коммит `24c264b54`) — по
интерливированным замерам гейта:

| Модуль | HEAD | baseline | Отношение |
|---|---|---|---|
| `src.backend.core.config.features` | 1.149 с | 0.731 с | **1.57×** |
| `src.backend.core.tenancy` | 1.122 с | 0.598 с | **1.88×** |
| `src.backend.dsl.registry.processor` | 1.003 с | 0.646 с | **1.55×** |
| `src.backend.dsl.registry.lazy_processor` | 0.797 с | 0.613 с | 1.30× |
| `src.backend.core.messaging` | 0.457 с | 0.485 с | 0.94× (без изменений) |
| `src.backend.services.routes.loader` | 0.662 с | 0.704 с | 0.94× (без изменений) |

Выросли ровно те модули, которые тянут цепочку `core.config.settings`.
По `-X importtime` и по замерам **внутри прод-образа**
(`import src.backend.core.tenancy` → **1.784 с**, 478 модулей, RSS 51 МБ):

* `src.backend.core.config.settings` — **1.05 с** в dev-окружении
  (на baseline ≈0.48 с): он eagerly импортирует **24 подмодуля конфигурации**
  (`ai`, `base`, `cert_store`, `clickhouse`, `database`, `dsl`, `elasticsearch`,
  `express`, `external_apis`, `external_databases`, `http_base`, `influxdb`,
  `lineage`, `mongo`, `plugin_loader`, `rag`, `security`, `services` (+11
  подмодулей), `telegram`, `transport`, `vault`, `workflow`);
* `pydantic_settings` — 358 мс (сторонний пакет, не наша зона);
* цепочка `pydantic_graph` → `logfire` → `rich` (≈110 мс) — **только
  dev-стоимость**: `logfire` объявляет pydantic-плагин через entry point
  (`[pydantic] logfire-plugin`), и pydantic подгружает его при создании
  первой модели. В прод-образе `logfire` **не установлен** (проверено:
  `logfire loaded in prod image: False`), поэтому эта ~110 мс на прод не
  относится — аналогично «+903 МБ» из §2.1 это свойство dev-venv.

**Что делать (по убыванию отдачи):**

1. **Разделить `core.config.settings` на «горячие» и «холодные» блоки.**
   Сейчас любой импорт конфигурации поднимает все 24 подмодуля; приложению
   на старте нужны единицы. Pydantic-settings это позволяет через ленивую
   подгрузку конкретных блоков (или через раздельные модели с
   `model_config`), но полностью ленивый `settings` невозможен: модели
   валидируются при импорте. Начинать с блоков, которые старту не нужны
   (influxdb, elasticsearch, lineage, telegram, cert_store).
2. **Убрать `rich` из стартовой цепочки** (в прод-образе он есть) — найти
   импортёра и отложить; ожидание — десятки мс.
3. Не трогать `pydantic_settings`: 358 мс — цена стороннего пакета.

**Приёмка:** отношение по каждому модулю ≤ 1.1× к коммиту `24c264b54`
(проверяется тем же гейтом), total старта в прод-образе ≤ 1.0 с
(сейчас 1.78 с на импорт одного модуля конфигурации).

### 3.3 Статус гейта стартового времени

Гейт переведён на **машинно-независимое сравнение**: он меряет тот же
набор модулей на коммите baseline'а в той же среде (git worktree), причём
замеры **интерливируются** — иначе дрейф нагрузки машины искажал отношение
(наблюдалось 2.45 при отсутствии регрессии). Печатается отношение и
покомпонентная разбивка (какой именно модуль потяжел).

Текущее состояние гейта — **красное и корректное**: он фиксирует реальную
регрессию стартового импорта (P8), которую прежние абсолютные пороги не
показывали. Принять текущее состояние как новый baseline (и перестать
фиксировать дальнейшую деградацию) — команда `--ratchet`.

## 4. Что сознательно не предлагаю

* **Не менять DI, `RouteBuilder`, plugin framework и набор протоколов** —
  аудит 2026-11-20 прямо исключил такой рефакторинг: он не устраняет
  функциональные дефекты и увеличивает регрессионную поверхность.
* **Не выносить маскирование «на потом» без метрики и политики** (P3) —
  тихая дыра в защите хуже медленного ответа.
* **Не удалять `torch`/`nvidia` из dev-venv** (5.2 ГБ) — это dev-среда, а не
  прод; в образ их нет. Если нужен «лёгкий» dev-образ — отдельная работа с
  extras.
