## 2. NEW-FOUND + FIXED: 16 Py2 `except X, Y:` syntax bugs

### 2.1 Background

In Python 2: `except ValueError, TypeError:` — catches both, binds second as `TypeError` (a class).

In Python 3: `except ValueError, TypeError:` parses as `except ValueError as TypeError:` —
catches ONLY `ValueError` and binds it to variable named `TypeError`. The intended `TypeError`
catch is silently dropped.

**Python 3.14 silent parse** is the dangerous case: the code is SYNTACTICALLY valid but
semantically wrong. Linters don't catch it because it's a valid parse.

### 2.3 Regression test (AST-based, not regex)

`tests/unit/test_py2_except_syntax_lint.py`:
- Parses all `.py` in `src/backend/` + `tests/` via `ast.parse`
- For each `ast.ExceptHandler` with `name` set, checks source line for comma between
  `except` and `as` (with unbalanced parens → Py2 pattern)
- **2/2 PASS** (src/backend + tests/)

Why AST and not regex:
- Regex catches false positives on string literals (test fixtures that contain Py2 examples)
- AST sees only actual `except` statements, ignores string content

### 2.4 Test result

```
tests/unit/test_py2_except_syntax_lint.py::test_no_py2_except_syntax_in_src_backend PASSED
tests/unit/test_py2_except_syntax_lint.py::test_no_py2_except_syntax_in_tests PASSED
======================== 2 passed, 6 warnings in 6.41s =========================
```

### 2.5 Why this matters

Most of these `except X, Y:` clauses are in **best-effort** paths (OTel API surface, MCP
tool kwargs injection, AI provider response parsing, gRPC stub injection). The intended
multi-type catch was a "narrow API-shape fallback" — but only the first type was actually
caught. Subsequent exception types propagated up, often crashing unrelated downstream code.

For example: `redelivery_policy.py:148` was supposed to catch `TypeError` AND `ValueError`
when parsing int attempt count. With Py2 syntax, only `TypeError` was caught, so a `ValueError`
from malformed int propagated up, possibly breaking reliability logic for malformed message
headers.

## 5. NEW-FOUND + REJECTED (false alarms, not real bugs)

### 5.1 `enforced_invoke.py:201` "fail-open"

```python
# src/backend/core/ai/gateway/orchestrator/enforced_invoke.py:201
try:
    from src.backend.core.audit.facade import emit_audit_safe
    emit_audit_safe(...)
except Exception:  # never fail caller
    pass
return None
```

**Claim**: Critical fail-open — caller receives `None` instead of 429/503 on budget_enforcer failure.

**Reality**: The `try/except` wraps ONLY `emit_audit_safe()` (audit event emission), NOT
the budget enforcement itself. The function is `_emit_audit_safe` wrapped in try/except.
If audit emission fails, the audit event is dropped (logged, but not blocking). This is
intentional "never fail caller" pattern for audit emission.

**Verdict**: NOT a bug. The budget_enforcer enforcement path (lines 204+) has its own
try/except for `BudgetBackendUnavailable` with proper 503 response.

### 5.2 Falsy-check patterns (3 sites)

```python
# src/backend/services/ai/rag_service/search_mixin.py:242
if self._cache is not None and results:  # cache lookup if results present
# src/backend/services/ai/hybrid_rag.py:126
if self._bm25 is not None and self._bm25_docs:  # hybrid search if BM25 docs present
# src/backend/services/ai/workflow_activities.py:172
if input_.structured_output_schema is not None and content_str:  # schema check if content
```

**Claim**: Falsy-check skip — empty dict/None confusion.

**Reality**: `if X is not None and Y:` correctly skips the branch when Y is empty/None.
The "falsy-check" pattern is the correct way to express "do this if both X and Y are present".
Catching all types of empty values (empty dict, empty list, None, 0, "") is the intended
behavior.

**Verdict**: NOT a bug. These are correct usage of `and` short-circuit.

### 5.3 ActionHandlerRegistry no Lock

**Claim**: Concurrent startup can lose handler (no Lock in `register()`).

**Reality**:
- Registry is populated at startup from `setup.register_action_handlers()` (sync function)
- `register_with_metadata` has cycle 133 atomic 3-way conflict check (line 134-195) — checks
  schema compatibility BEFORE any mutation
- Simple `register()` (line 81-117) is called sequentially during sync init
- After init, registry is read-only (no `unregister`)

**Verdict**: NOT a real race condition. The atomic check in `register_with_metadata`
prevents the main concern (incompatible schema overwrite).
